# Lindsey Wegmann Portfolio Website — Build Requirements

## 1. Project summary

Build a fast, accessible, content-managed portfolio website for Lindsey Wegmann, a Senior Digital Strategist. The site should establish her credibility, show how she thinks, highlight selected work, and make it easy for recruiters, employers, collaborators, or prospective clients to contact her.

The personality should feel bright, clever, warm, and direct—not corporate or overly polished. Use subtle Taylor Swift-inspired language and golden-retriever moments as personality accents, never as the main concept.

The site must include:

- A public portfolio website
- A secure admin area
- A modular page builder for public pages
- A blog with drafts, previews, scheduling, categories, and SEO controls
- Project/case-study management
- Privacy-conscious analytics and conversion tracking
- Contact form management and spam protection
- Responsive, accessible, search-friendly rendering

## 5. Brand and creative direction

### Brand attributes

- Strategic but plainspoken
- Smart without sounding self-important
- Warm, optimistic, and energetic
- Organized and outcome-oriented
- Playful in small, rewarding moments

### Visual direction

- Light backgrounds: warm white, cream, pale blush, soft lavender, and restrained golden accents
- Dark charcoal or deep plum text with WCAG-compliant contrast
- Generous whitespace and simple editorial layouts
- Rounded cards used selectively; avoid making everything look like a generic SaaS dashboard
- One expressive display typeface for headings and one highly readable sans-serif for body copy
- Photography should feel candid and natural rather than like corporate stock photography
- Golden-retriever visuals should use Lindsey's own approved photos or properly licensed assets

### Taylor Swift-inspired approach

Use subtle, original nods that fans may recognize, such as eras, chapters, hidden details, friendship-bracelet-like tags, or an occasional “in my ___ era” label. Do not use song lyrics, album artwork, Taylor Swift's likeness, official logos, tour branding, copyrighted audio, or language that implies endorsement.

Suggested optional moments:

- Case-study filters presented as “eras” while retaining a plain accessible label
- A tiny sparkle interaction on a meaningful CTA
- A tasteful “currently in my…” status line editable in the admin
- A site-wide Easter-egg toggle that reveals a few extra microcopy details
- A golden retriever illustration or photo near the 404 page and contact confirmation

All playful features must be removable in the admin and must respect `prefers-reduced-motion`.

### Voice

- Use short sentences, active voice, and concrete outcomes
- Prefer “Here’s how I approach it” to abstract agency language
- Avoid buzzword piles such as “full-funnel omnichannel transformation”
- Use first person throughout unless Lindsey chooses otherwise
- Humor should be brief and never obscure navigation, calls to action, or form guidance

## 8. CMS and admin requirements

Use Filament 5 for the administrative interface unless a concrete compatibility issue appears during implementation.

### Roles

- `super_admin`: all settings and user management
- `editor`: pages, posts, projects, media, redirects, menus, form submissions
- `author`: own posts and drafts only

Enforce authorization through Laravel policies, not hidden navigation alone.

### Dashboard

- Draft and scheduled content counts
- Recent form submissions
- Recently edited content
- Broken or missing metadata warnings
- Analytics summary when configured
- Quick-create actions for post, project, and page

### Page builder

Pages are composed from ordered, reusable block records or validated JSON blocks. Do not store an entire page as unrestricted HTML.

Required blocks:

- Hero
- Rich text
- Image + text
- Full-width image
- CTA banner
- Card grid
- Capabilities/services grid
- Featured projects
- Featured/latest posts
- Testimonial(s)
- Stats/results
- Timeline
- Logo strip
- FAQ
- Quote/pull quote
- Embed with an allowlist
- Spacer/divider with limited preset sizes
- Personality/Easter-egg block

Each block must support:

- Visible label in the admin
- Enable/disable without deleting
- Drag-and-drop ordering
- Block-specific validation
- Optional anchor ID
- Background/style preset from a controlled design system
- Responsive image fields and meaningful alt text
- Preview state

Do not allow arbitrary colors, fonts, scripts, iframes, or layout CSS in routine editor controls.

## 9. Analytics and tracking

Build an analytics abstraction rather than scattering vendor calls through templates.

Preferred initial implementation:

- Google Tag Manager + GA4 if Lindsey wants mainstream marketing analytics, or Plausible/Umami if privacy and simplicity are preferred
- Environment-specific IDs; no production events from local/test environments
- Consent mode/cookie banner only when required by the selected tools and audience
- Respect Do Not Track where practical
- Never send contact form contents, email addresses, names, or other personal data to analytics

Track these named events consistently:

- `cta_click` with placement and label
- `case_study_view`
- `resume_download`
- `contact_form_start`
- `contact_form_submit`
- `outbound_link_click` with destination category
- `blog_post_view`
- `blog_filter_use`
- `site_search`
- `not_found_view`

Document the event schema in the repository. Provide a browser-console debug mode for non-production environments.

## 11. Accessibility

Target WCAG 2.2 AA.

- Full keyboard operation and visible focus states
- Skip link and semantic landmarks
- Logical heading structure
- Text/background contrast compliant in every design preset
- Form labels, descriptions, and accessible error summary
- Alt text required for meaningful images; decorative images use empty alt text
- No autoplay audio or video
- Motion honors `prefers-reduced-motion`
- Easter eggs cannot be required to understand or navigate the site
- Minimum practical touch targets and responsive zoom support
- Automated accessibility tests plus manual keyboard and screen-reader spot checks

## 12. Technical architecture

### Baseline stack

- PHP 8.4+
- Laravel 13
- PostgreSQL 16+ in production; SQLite permitted for local automated tests
- Blade + Livewire 4 + Alpine.js for the public site and interactive components
- Filament 5 for admin
- Tailwind CSS 4
- Vite
- Redis for cache, queues, and rate limiting in production
- S3-compatible media storage in production
- Laravel scheduler and queue worker

Prefer server-rendered pages over a client-heavy SPA. Use JavaScript only where it materially improves the interaction.

### Suggested packages

- `filament/filament`
- `spatie/laravel-medialibrary`
- `spatie/laravel-permission` if policies/role needs justify it
- `spatie/laravel-sitemap` or a small application-owned sitemap implementation
- `spatie/laravel-backup`
- `spatie/laravel-activitylog` for admin audit history
- `league/commonmark` only if Markdown blocks are included

Validate current Laravel 13 and Filament 5 compatibility before installing every package. Avoid adding a package when first-party Laravel/Filament functionality is sufficient.

- `PostRevision`

- `Tag`
- `Project`
- `ProjectMetric`

- `ContactSubmission`

Use enums for publish status and other closed state sets. Store timestamps in UTC and display/administer them in the configured site timezone.

### Content rendering

- Map every builder block type to a dedicated data object/schema and Blade component
- Whitelist block types and style variants
- Escape plain text by default
- Sanitize any rich text on write and render
- Allow only approved embed providers and URL patterns
- Cache rendered public content and invalidate on relevant content changes
- Draft and scheduled content must never leak into public queries, sitemap, RSS, or related-content results

## 13. Contact form and privacy

- Validate server-side and client-side
- CSRF protection
- Honeypot plus time-based trap
- Per-IP and per-email rate limits without exposing which value triggered the limit
- Optional Cloudflare Turnstile after normal anti-spam controls prove insufficient
- Queue notification email to the configured recipient
- Store submissions with status: new, read, replied, archived, spam
- Add configurable retention and a scheduled purge; default recommendation: 12 months
- Escape submission content in admin and notification emails
- Do not send an automatic marketing subscription unless the visitor explicitly opts in
- Log delivery failure without logging private message content

## 14. Performance and reliability

Targets for representative production pages on mobile at the 75th percentile:

- LCP <= 2.5 seconds
- INP <= 200 ms
- CLS <= 0.1
- Lighthouse performance target >= 90 as a build indicator, not a substitute for field data

Implementation expectations:

- Responsive images with explicit dimensions
- Lazy-load below-the-fold media
- Self-host and subset fonts when licensing permits
- Minimal third-party scripts
- Page and query caching with explicit invalidation
- Database indexes for public status/date/slug lookups and admin filters
- Queue email and expensive media work
- Health endpoint suitable for the hosting platform
- Daily database backup and documented restore process
- Error monitoring integration through an environment-configured provider

## 15. Security

- Admin authentication with email verification and optional/encouraged MFA
- No public registration
- Strong authorization policies for every admin resource/action
- Rate-limit login, preview, forms, and sensitive endpoints
- Signed expiring preview links
- Secure cookies, HTTPS, CSP, HSTS, and standard security headers in production
- Validate upload MIME type, extension, size, and image decoding
- Sanitize SVG or disallow it for ordinary editors
- Never store credentials or vendor secrets in the database unless encrypted and necessary
- Audit log for admin content changes, settings changes, and sign-ins
- Dependencies checked in CI

## 16. Testing requirements

Use Pest or PHPUnit consistently; do not mix styles without reason.

Required automated coverage:

- Public route and published-content visibility tests
- Draft/scheduled/archived content exclusion
- Page-block validation and rendering for every block type
- Admin policy/role tests
- Contact validation, throttling, spam controls, queueing, and successful submission
- Redirect behavior and slug history
- Sitemap, RSS, canonical, and metadata tests
- Analytics event payload tests with PII exclusions
- Media upload validation
- Signed preview authorization and expiration
- Accessibility smoke tests with axe on key templates
- Responsive end-to-end tests for home, work, post, and contact flows

Use factories and seeders. Demo data must be obviously fictional and must not be deployable as Lindsey's real history by mistake.

## 17. CI/CD and environments

- Environments: local, staging, production
- CI runs formatting, static analysis, tests, asset build, and dependency audit
- Recommended PHP tooling: Laravel Pint and Larastan/PHPStan
- Deploy with zero/minimal downtime and run migrations safely
- Queue worker and scheduler configured in staging/production
- Separate storage, mail, analytics, and search credentials by environment
- Staging must be protected from indexing and analytics contamination
- Provide `.env.example` with every required variable and no secrets

## 18. Admin/editor acceptance criteria

An editor can:

- Create a draft page from approved blocks, reorder it, preview it, schedule it, and publish it without code changes
- Create and schedule a post with images, categories, metadata, and related posts
- Create a case study and feature it on the home page
- Change navigation labels/order without editing templates
- Replace the resume and default social image
- Update SEO/social metadata for any page, post, or project
- Disable playful site features without developer help
- Review and archive contact submissions
- Create a 301 redirect

The system prevents an editor from:

- Injecting arbitrary scripts or unsafe iframes
- Selecting inaccessible color combinations
- Publishing a record missing required content or metadata
- Seeing or changing actions outside their role
- Accidentally deleting media currently used by content

## 19. Public-site acceptance criteria

- Every primary page is responsive from 320px through large desktop widths
- Header, footer, page titles, CTAs, and contact paths are consistent
- Core content is usable with JavaScript disabled
- Keyboard-only users can complete the contact flow
- Reduced-motion users receive no nonessential movement
- Published content appears in sitemap/RSS as appropriate; drafts never do
- Contact success is shown only after the server accepts the submission
- Analytics fires the documented event once and contains no PII
- All major templates meet WCAG 2.2 AA checks and performance targets
- No Taylor Swift copyrighted media, lyrics, or implied endorsement is used
